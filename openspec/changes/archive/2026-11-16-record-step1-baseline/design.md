# Design

## Context

手順 1 の実装は `apps/cli` にある（proposal.md の Why を参照）。core.db の扱いとマイグレーションは kotlin-core-app の lib/core が持ち、CLI は composite build（`includeBuild("../kotlin-core-app")`）でそれを取り込む。この design は、仕様（specs/）を満たすために選んだ方式と、その理由を記録する。

## Goals / Non-Goals

**Goals:**

- コマンドを足すたびに --json の形と終了コードがぶれないよう、共通の仕組みに寄せる
- CLI を lib/core の上の薄い層に保ち、ドメインの規則を CLI に書かない

**Non-Goals:**

- user 以降のコマンド（手順 2 で作る）
- --actor の実装（最初の書き込みのコマンドで実装する）

## Decisions

### 処理をするコマンドは共通の基底から作る

--json と結果の出し方を共通の基底にまとめ、core.db を使うコマンドはさらに --db の基底を使う。各コマンドは data の型と人向けの表示だけを書く。data は型を決めたクラスから JSON にするので、項目の名前と型が変わるとコンパイルとテストで気づける。

- 代わりの案: コマンドごとに JSON を組み立てる → 外側の形がぶれやすいので採らない

### 失敗は 1 か所で JSON と終了コードに変える

コマンドは失敗の種類（ErrorCode）と理由を投げ、入口の 1 か所でそれを JSON または標準エラーの文と終了コードに変える。引数の解析に失敗したときは、--json を付けたかどうかを生の引数から判断する。解析に失敗するとオプションの値が得られないため。

### .env は自前で読み、環境変数で上書きする

.env を読んで環境変数と合わせ、引数の解析器が環境変数を読む口に渡す。書式は KEY=VALUE とコメント・引用符だけを扱う。依存を増やさないため、ライブラリは使わない。

### ログは捨てる

Flyway と jOOQ のログやロゴが標準出力の JSON に混ざらないよう、CLI ではログの出力先を何もしないものにし、jOOQ のロゴも止める。失敗の理由は例外から JSON・標準エラーに出す。

## Risks / Trade-offs

- [ログを捨てるので、想定外のエラーの調べが付きにくい] → INTERNAL の message に例外の種類と文を入れる。必要になったら、標準エラーにログを出すオプションを足す
- [--json の判断を生の引数で行うので、オプションの値として "--json" を渡すと誤判定する] → 試作では許容する
